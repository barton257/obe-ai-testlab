# Bug 严重级别（Severity）判定标准

**用途**：给每个缺陷打 S1–S4 标签，决定处理时限和资源投入。
**适用范围**：所有业务模块。
**关系**：本文档是 [AGENTS.md](../../AGENTS.md) 第五节的细化。冲突时以 AGENTS.md 为准。

---

## 一、四级定义

| 级别 | 名称 | 一句话定义 | 处理时限 | 是否阻塞上线 |
|---|---|---|---|---|
| **S1** | 致命 (Critical) | 造成资金损失、数据错乱、生产宕机、可越权 | **立即**（发现即处理，可停版） | ✅ 是 |
| **S2** | 严重 (Major) | 主功能异常、影响多数用户，无对等 workaround | **当天** | ✅ 是（灰度可继续） |
| **S3** | 一般 (Normal) | 功能可用但不符合设计、体验差、埋雷 | **≤ 2 周**（下个迭代） | ❌ 否 |
| **S4** | 轻微 (Minor) | 优化建议、极少数用户、边缘场景、纯文案 | **无期限**（有空再修） | ❌ 否 |

---

## 二、判定树

从上到下匹配，命中即停：

```
1. 会不会导致真金白银错动或丢失？
   ├─ 是 → S1
   └─ 否 → 2

2. 会不会让用户看到别人的数据 / 操作别人的账户？
   ├─ 是 → S1
   └─ 否 → 3

3. 生产环境是否已经/即将发生？
   ├─ 是 → S1
   └─ 否 → 4

4. 是否阻塞了核心业务主路径（例：登录/订阅/赎回）？
   ├─ 是 → S2
   └─ 否 → 5

5. 影响的用户占比大不大（> 10%）？
   ├─ 是 → S2
   └─ 否 → 6

6. 是否有对等的 workaround（用户能绕开）？
   ├─ 没有 → S2
   └─ 有 → 7

7. 是否不符合设计 / 埋了隐患（未来重构可能引爆）？
   ├─ 是 → S3
   └─ 否 → 8

8. 剩下的 → S4
```

---

## 三、SLA 处理时限

| 级别 | 首次响应 | 修复窗口 | 上线要求 |
|---|---|---|---|
| S1 | ≤ 30 min | ≤ 24 h | 必须回归验证 + Hotfix 通道 |
| S2 | ≤ 2 h | ≤ 3 天 | 必须回归验证 + 正常发版 |
| S3 | ≤ 1 天 | ≤ 2 周 | 计入下个迭代 |
| S4 | ≤ 1 周 | 无期限 | 有空排 |

**超期升级**：S1 超 24h 未修 → 升级到 CTO；S2 超 1 周未修 → 升级到部门负责人。

## 四、示例（斯巴达业务）

| 现象 | 判定 | 依据 |
|---|---|---|
| 赎回超权益真的把资金池的钱扣走了 | **S1** | 步骤 1 命中，资金错动 |
| 用 User1 token 传 User2 UID，钱真的从 User2 扣 | **S1** | 步骤 2 命中，越权 |
| 生产环境批次调度器挂了，所有订阅停在 Init | **S1** | 步骤 3 命中，生产宕机 |
| 订阅金额 `amount=0.5`（低于 min=1）穿透校验，记录了 0.5 USDT 订阅 | **S2** | 步骤 4：主路径异常但没跨用户；步骤 5：影响所有走该路径的用户 |
| 赎回 `settleAmount=999999999` 同步返回 success（等批次结果） | **待批次确认**：若真扣 → S1；若批次拒绝但用户等 10min 才看到 → S2 |
| body.userId 与 JWT.api 不匹配未拒绝，但服务端以 JWT 为准，不越权 | **S3** | 步骤 7：埋雷，未来 refactor 可能引爆 |
| 订阅确认弹窗中"最小金额"文案漏翻译，其他文字正常 | **S4** | 步骤 8：纯文案 |
| Safari 下机器人卡片阴影错位 5px | **S4** | 步骤 8：视觉细节 |
| Mobile Web 下订阅按钮被键盘遮住需要滚动 | **S3** | 步骤 6：能滚开算 workaround，但不符合设计 |

## 五、模糊边界处理

**A. "可能造成资金损失"但未证实**

- 例：`redeem settleAmount=999999999` 同步 success，但批次结果未知
- **默认按最严重级别（S1）报**，等验证后调整
- 报告标题写"初报 S1（潜在<原因>）→ 复现后确认 S<x>"
- 现例：[`2026-08-17-spartans-S3-userId与JWT不匹配未拦截.md`](../../projects/spartans/bugs/) 就是从 S1 降为 S3 的样例

**B. 一个 bug 触发多个后果**

- 取**最高级别**。例：赎回失败同时导致资金卡住 + UI 白屏 → 按 S1（资金卡住）处理

**C. 只在特定条件复现**

- 复现率影响严重级别吗？**不影响 S 级别，影响 P 优先级**
- 例：只在慢网下 20% 概率出现的越权 → 仍是 S1，只是 P 可能是 P1 而不是 P0

**D. 前端 vs 后端归属**

- **不影响 S 级别**，只影响 assignee
- 前端把风险披露勾选状态清空但后端未校验，用户能绕过 → 判 S1/S2 看后端能否兜住

## 六、S 与 P 的关系

严重级别 (S) 描述 bug 有多严重；优先级 (P) 描述何时排期。两者独立，但通常关联：

| S | 默认 P | 例外 |
|---|---|---|
| S1 | P0 | 无 |
| S2 | P0 或 P1 | 影响用户占比小可降 P1 |
| S3 | P1 或 P2 | 埋雷严重可升 P1 |
| S4 | P2 或 P3 | 品牌敏感文案可升 P1 |

优先级判定见 [`priority.md`](priority.md)（待补）。

## 七、命名规范提醒

Bug 文件名：`YYYY-MM-DD-{业务}-{S1..S4}-{简述}.md`（见 AGENTS.md 第三节）

**S 级别更改**必须同步：

1. 改文件名（`git mv` 保留历史）
2. 改文件内首行标题的 `[Sx]`
3. 在文件里保留一段"级别调整记录"，说明升降级理由

## 八、常见错误

- ❌ 把"接口设计不严谨"当 S1（不符合设计但不出事 → S3）
- ❌ 把"生产偶发 5% 失败"当 S3（偶发但影响所有用户主路径 → S2）
- ❌ 把"越权可能性"当 S3（可能就按 S1 报，验证后再降）
- ❌ 把"UI 错位但功能正常"当 S2（视觉问题一般 S3/S4）
- ❌ 只看现象不看后果打级（现象轻但后果重仍是高级别）
