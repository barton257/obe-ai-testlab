# 任务优先级（Priority）判定标准

**用途**：给每个任务打 P0–P3 标签，决定排期顺序。
**适用范围**：所有业务模块的测试任务、缺陷修复、基建与文档工作。
**关系**：本文档与 [`bug-severity.md`](bug-severity.md) 配套 —— S 描述"缺陷有多严重"，P 描述"事情什么时候做"。

---

## 一、四级定义

| 级别 | 名称 | 一句话定义 | 排期窗口 | 是否阻塞上线 |
|---|---|---|---|---|
| **P0** | 紧急 | 阻塞上线或阻塞其他人干活 | **本周** | ✅ 是 |
| **P1** | 高 | 本次迭代必须交付，不做会累积成技术债 | **本迭代**（约 3 周） | ❌ 否 |
| **P2** | 中 | 该做但可以等下个迭代 | **下个迭代** | ❌ 否 |
| **P3** | 低 | 想做、有价值，但没有时间压力 | **无期限** | ❌ 否 |

---

## 二、判定树

从上到下匹配，命中即停：

```
1. 是不是 S1/S2 缺陷？
   ├─ 是 → P0
   └─ 否 → 2

2. 别人是否正在等这件事才能开工（阻塞他人）？
   ├─ 是 → P0
   └─ 否 → 3

3. 是否阻塞本次上线的 DoD 闸门？
   ├─ 是 → P0
   └─ 否 → 4

4. 不做会不会让已有测试资产失效 / 持续产生错误结论？
   ├─ 是 → P1
   └─ 否 → 5

5. 是不是本迭代交付范围内功能的配套测试？
   ├─ 是 → P1
   └─ 否 → 6

6. 是否已经有明确的需求方在等（产品/后端/SRE）？
   ├─ 是 → P1
   └─ 否 → 7

7. 是否为下个迭代已排期功能做准备？
   ├─ 是 → P2
   └─ 否 → 8

8. 剩下的（探索性、锦上添花、长期优化）→ P3
```

---

## 三、排期窗口

| 级别 | 认领时限 | 交付窗口 | 超期处理 |
|---|---|---|---|
| P0 | 当天 | ≤ 本周 | 周会上报，必要时换人接手 |
| P1 | ≤ 3 天 | ≤ 本迭代末 | 迭代复盘说明原因，决定顺延或降级 |
| P2 | 无 | ≤ 下个迭代末 | 连续顺延两个迭代 → 降 P3 或关闭 |
| P3 | 无 | 无 | 每季度清一次，无人认领则关闭 |

**升级触发**：P1 任务如果开始阻塞他人 → 立即升 P0；P2 如果对应功能提前进入迭代 → 升 P1。

## 四、示例（斯巴达业务）

| 任务 | 判定 | 依据 |
|---|---|---|
| 后端修复 S2 订阅金额穿透 | **P0** | 步骤 1：S2 缺陷 |
| Playwright 全量跑登录态失效排查 | **P0** | 步骤 4：会让断言结论反转，持续产生错误结论（2026-08-18 实例：已误导过一次用例审查） |
| 补 `shared/conventions/priority.md`（本文档） | **P0** | 步骤 2：bug-severity.md 已引用它，缺失时 P 级判定无依据 |
| 跑一次完整 API E2E 验证数据链 | **P0** | 步骤 3：DoD 要求主链路验证通过 |
| 评审 TEST_STRATEGY 的 5 条待确认项 | **P1** | 步骤 6：需要产品/后端拍板，但不阻塞当前用例编写 |
| 给 happy path 补"最新记录金额+时间"断言 | **P1** | 步骤 4：断言过弱会让缺陷漏过，属于测试资产失效 |
| 资金类测试的专用账户与数据清理方案 | **P1** | 步骤 4：没有它，动账用例无法重复跑 |
| 赎回 / 分润 HWM 模块 TEST_STRATEGY | **P1** | 步骤 5：本迭代覆盖范围内 |
| 契约测试骨架 `automation/contracts/` | **P2** | 步骤 7：为后续接口联调做准备 |
| 压测 subscribe 100 QPS | **P2** | 步骤 7：下个迭代性能目标 |
| Playwright 跨浏览器矩阵（WebKit/Firefox） | **P2** | 步骤 7：当前只需 Chromium 覆盖 |
| Chaos 测试（DB 主备切换） | **P3** | 步骤 8：探索性 |
| 无障碍性 accessibility 扫描 | **P3** | 步骤 8：暂无合规要求驱动 |

## 五、模糊边界处理

**A. 缺陷等级与任务优先级不一致**

以 S 级为下限，可以往上调不往下调：

- S1/S2 → 至少 P0
- S3 但埋雷严重（未来 refactor 会引爆） → 可升 P1
- S4 但涉及品牌敏感文案 → 可升 P1

**B. 复现率低的缺陷**

复现率**不影响 S 级，影响 P 级**：

- 只在慢网下 20% 概率复现的越权 → 仍是 S1，但排期可能是 P1
- 100% 复现的文案错误 → 仍是 S4，但如果一眼可见可升 P1

**C. "顺手就能做"的小任务**

耗时 < 15 min 且零风险的任务，即使判定为 P2/P3，也可以在做 P0/P1 时顺手带上。
**但不允许**因为"顺手"而挤占 P0 的时间。

**D. 依赖外部方的任务**

如果任务依赖后端/产品/SRE，**先把不依赖的部分做完**，依赖部分标注阻塞原因。
不要因为"等别人"就把整个任务挂起 —— 见 AGENTS.md 的交付要求。

**E. 测试基建 vs 业务用例**

基建（CI、page-objects、客户端封装）通常 P1/P2，但如果**没有它就写不了 P0 用例**，
则跟随被阻塞用例的优先级升到 P0。

## 六、P 与 S 的关系

| S | 默认 P | 例外 |
|---|---|---|
| S1 | P0 | 无 |
| S2 | P0 或 P1 | 影响用户占比小可降 P1 |
| S3 | P1 或 P2 | 埋雷严重可升 P1 |
| S4 | P2 或 P3 | 品牌敏感文案可升 P1 |

注意：**并非所有 P0 都来自缺陷**。基建、文档、评审同样可以是 P0
（判定树步骤 2/3），此时没有对应的 S 级。

---

## 七、命名与记录规范

- Roadmap 文件：`YYYY-MM-DD-{主题}.md`（见 AGENTS.md 第三节）
- 任务编号：`P{级别}-{序号}`，例 `P0-3`、`P1-12`
- 用例文件名里的 P 级指**用例本身的重要程度**（`spartans-subscribe-P0-正常-最小订阅金额.yaml`），
  与任务排期的 P 级同标准但独立取值 —— 一条 P0 用例可能由一个 P1 任务来补齐

**P 级变更**需在 roadmap 里保留一行变更说明，写明升降级理由与日期。

---

## 八、常见错误

- ❌ 把"我最想做的"当 P0（个人兴趣 ≠ 优先级）
- ❌ 把所有缺陷都打 P0（S3/S4 缺陷通常 P1/P2）
- ❌ 因为任务大就降级（拆分它，而不是往后推）
- ❌ 因为任务小就升级（顺手做掉，不占 P0 名额）
- ❌ 忘记"阻塞他人"这条 —— 自己看着不急的事，可能正卡着别人
- ❌ 依赖外部方就整体挂起（应拆出可做部分先交付）
