# regression-planner / cases

**已解决过的真实案例**归档。记录：AI 生成的回归清单 → 实际测下来的补充/删减 → 原因。

同类目录说明见 `../../testcase-generator/cases/README.md`。

## 什么时候写一个 case

**regression-planner 触发条件**（比其他 skill 更晚触发，因为需要"实际跑过"才有反馈）：

- AI 漏了受影响的关联模块（改了 A，其实 B 也依赖）
- AI 列了不必要的回归项（浪费时间）
- 优先级判断偏差（把关键路径列在末尾）
- 未识别数据迁移/配置变更的影响面
- 未考虑上下游依赖（前端改了但后端接口也变了）

不写：清单顺序调整、单个用例增删。

## 结构

沿用三段式：**Input**（变更描述）+ **AI First Draft**（回归清单）+ **Final Version**（实际执行后的清单 + 增删原因），加一段 **学习点**。

## regression-planner 案例的特有关注

写案例时着重记录：

1. **变更影响面推理**——AI 从哪些线索识别出关联模块（代码 diff / 配置 / 数据库 / 文档）
2. **漏测代价评估**——为什么这条不能漏（用户量 / 资金安全 / SLA）
3. **裁剪依据**——为什么这条可以跳（覆盖率已足 / 无实质影响 / 成本过高）
4. **上下游联动**——前后端 / 服务间的隐性依赖如何被识别

## 触发时机

需要一次**真实的迭代闭环**：变更 → AI 生成清单 → 实际执行 → 复盘漏测/多测。
