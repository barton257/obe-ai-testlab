# bug-writer / cases

**已解决过的真实案例**归档。记录：AI 写的原始 bug 报告 → 人工修改后的终版 → 修改原因。

同类目录说明见 `../../testcase-generator/cases/README.md`。

## 什么时候写一个 case

**bug-writer 触发条件**：

- AI 判错了严重级别（把 S1 写成 S3 或反过来）
- 复现步骤缺关键前置条件
- 现象描述用了内部黑话或研发看不懂的用户视角
- 缺了影响范围 / 绕过路径 / 数据一致性说明
- 附件类型判断错（该要日志给了截图、该要 HAR 给了描述）

不写：措辞润色、标点修改。

## 结构

沿用 testcase-generator 案例的三段式：**Input** + **AI First Draft** + **Final Version**，加一段 **学习点**（提炼可复用的判断规则）。

## bug-writer 案例的特有关注

写案例时着重记录：

1. **严重级别判断依据**——"这个为什么是 S2 而不是 S3"，让 AI 学到你的分级心智模型
2. **信息完整度阈值**——"复现率不到 3/3 我要求先补测"这类隐性规则
3. **脱敏边界**——"这个字段可以留，那个必须打码"
