# [S2] 订阅金额 0.5 USDT 未被拦截

- 环境：Testnet / API `bullapitest.1bullex.com`
- 复现率：1/1
- 提交人：Barton（AI 辅助）
- 日期：2026-08-17
- 影响接口：`POST /botapi/v1/invest/purchase`

## 复现步骤

```bash
curl -X POST 'https://bullapitest.1bullex.com/botapi/v1/invest/purchase' \
  -H 'authorization: Bearer <user1_token>' \
  -H 'content-type: application/json' \
  --data '{"userId":"10732164","botId":1342,"amount":0.5}'
```

## 预期

- 按 Tier 参数最小订阅金额为 1 USDT（`shared` 口径 / 运营配置）
- 应拒绝并返回 `{"code":1,"msg":"amount_below_min"}` 或类似业务错误

## 实际

- `{"code":0,"msg":"success","data":null,"timestamp":0}`
- `invest/history` 中出现 `tradeAmount=0.5, status=Init` 的记录

## 复现附件

见相邻用例 `tests/api/test_spartans_api.py::TestPurchaseErrorBranches::test_purchase_amount_zero_rejected`；下沉边界值 0.5 会命中此 bug。

## 备注

`amount=0` 会正确返回 `amount_not_allowed`，只有 `0 < amount < 1` 时穿透。疑似最小值校验用了 `> 0` 而非 `>= min_subscribe`。

---

## 复验记录 2026-08-18（Barton，AI 辅助）

**状态：缺陷仍存在，未修复。** 后端仓库不在本机，用 Testnet 实调复验。

原报告「疑似校验用了 `> 0` 而非 `>= min_subscribe`」的猜测**已被证实**，且实际影响比原报告更大：

| 输入 amount | 结果 |
|---|---|
| 0.5 / 0.999 / 0.01 | 穿透，`code=0 success` |
| 0.001 / 0.0001 / **1e-08** | 穿透 |
| 0 | 拦截 `amount_not_allowed` |
| -1 | 拦截 `amount_not_allowed` |

拦截边界恰好是 `amount > 0`。**`min_subscribe=1` 这个 Tier 配置在 purchase 路径上完全没有被读取** ——
不是阈值取错，是最小值校验整体缺失。

### 比原报告更严重的两点

**① 数据污染面**

可用极小额度刷出任意多条订阅记录。本次复验即产生 6 条
（`#1831` amt=0.5、`#1832` amt=0.999、`#1833` amt=0.01、`#1836` amt=0.001、
`#1837` amt=0.0001、`#1838` amt=1e-08）。单个账户能以近乎零成本膨胀
invest_history 与批次队列。

**② 极小额度产生永久卡单（新发现，原报告未覆盖）**

跨越至少一个完整批次窗口后复查各笔的终态：

| 记录 | amount | status | tradeUnits |
|---|---|---|---|
| `#1838` | **1e-08** | **`Locked`** | **0** |
| `#1837` | 0.0001 | `Finished` | 0.000101 |
| `#1836` | 0.001 | `Finished` | 0.001016 |
| `#1833` | 0.01 | `Finished` | 0.01016 |
| `#1832` | 0.999 | `Finished` | 1.015007 |
| `#1831` | 0.5 | `Finished` | 0.508011 |

`1e-08` 那笔**卡在 `Locked` 且 `units=0`，批次无法处理也不回滚**。
推测原因：份额铸造按精度舍入后为 0，批次逻辑无法处理零份额记录，
既不能完成也不能失败，成为永久悬挂状态。

这使缺陷后果从"脏数据"升级为**可构造的卡单**：攻击者可批量提交
`1e-08` 订阅，在批次队列里堆积无法消化的 `Locked` 记录。

### 级别评估

严重级别**维持 S2**（未跨用户、未错动他人资金，仍有 workaround）。
但结合 ② 的卡单效应，建议修复排期**置于本周 P0 首位** ——
按 [`priority.md`](../../../shared/conventions/priority.md) 判定树步骤 1，S2 缺陷即 P0。

⚠️ 遗留待清理：`#1838` 这条 `Locked` 记录需要后端介入清理，QA 侧无法自行消除。

### 修复建议

purchase controller 补最小值校验：

```
if amount < tier.min_subscribe:
    return {"code": 1, "msg": "amount_below_min",
            "data": {"minAllowed": tier.min_subscribe}}
```

要点：

1. 阈值必须从 Tier 配置读取，**不要写死 1** —— 运营可调整（见 `tests/fixtures/tier_config.yaml`）
2. 保留现有 `amount_not_allowed`（`amount <= 0`）分支，与 `amount_below_min` 是不同语义：
   前端需要区分"金额非法"和"低于起投额"，后者要能提示具体最小值
3. 建议同时校验小数精度上限，避免 `1e-08` 这类输入进入金额计算

**另需单独处理卡单（对应新发现 ②）**：即使补齐了入口校验，
批次逻辑对"份额铸造后为 0"的记录仍应有兜底，否则任何精度边界都可能再次造成
`Locked` 悬挂。建议批次侧增加：

```
if mintedUnits == 0:
    mark_record_failed(record, reason="units_rounds_to_zero")  # 显式失败并退款
```

即"宁可失败回滚，不要永久挂起" —— 与本缺陷家族"显式拒绝优于静默处理"是同一原则。

### 关联
